01 / Foundation

Identity & naming conventions

Bedrock Add-Ons are not identified by an npm-style package name. They use UUID-based pack manifests; custom content is identified through namespaced identifiers.

PurposeConvention
Public nameSinbad Selection
GitHub repositoryasa-minecraft-package
npm packageasa-minecraft-package (if used)
Content namespacesinbad
Behavior PackSinbad Selection - Behavior
Resource PackSinbad Selection - Resources
Release artifactasa-minecraft-package-vX.Y.Z.mcaddon
Release version1.0.0 initial stable target

Example content identifiers

sinbad:cosmic_jellyfish
sinbad:lightning_centipede
sinbad:cosmic_sword
sinbad:giant_pacific_raindrop
Compatibility invariant: Generate separate UUIDs for the Behavior Pack, Resource Pack, and appropriate modules. Commit them once and retain them across updates. Increase manifest versions for new releases. Keep existing content identifiers stable.

04 / Collaboration

From your son's picture to Minecraft

Drawing / concept→Codex Explore→OpenSpec Proposal→Human approval→AI implementation→Preview & tests→Codex Review→Release

Core working rules

  • Archive original art and distinguish the child's explicit ideas from AI interpretations.
  • Explore feasibility and identify whether behavior is JSON-native or needs Script API.
  • Create an OpenSpec proposal with acceptance criteria before implementation.
  • Have a human approve the proposal before an AI agent implements it.
  • Review the implementation against the proposal in the original Codex exploration session.
  • Archive the completed OpenSpec change only after verification.

# Project Handoff: Sinbad Selection

## Project overview
Initiate a GitHub repository named `asa-minecraft-package`.

Sinbad Selection is a continuously growing Minecraft Bedrock Edition Add-On featuring original mobs, bosses, skills, weapons, items, and gameplay content developed collaboratively by a parent and child. The child supplies creative ideas, descriptions, and reference images. The parent manages technical decisions, AI-assisted exploration, implementation, testing, and releases.

Target Minecraft Bedrock Edition on iOS, including compatibility with existing worlds wherever feasible.

## Architecture decisions
1. One GitHub repository and one distributed `.mcaddon` per version.
2. Bundle all content into a single growing Add-On.
3. Public name: `Sinbad Selection`.
4. Namespace for custom content: `sinbad`.
5. Use TypeScript where Bedrock Script API logic is required; compile to compatible JavaScript.
6. Maintain distinct Behavior Pack and Resource Pack structures with correct manifest dependencies.
7. Preserve UUIDs, custom identifiers and compatibility across releases.
8. Follow the current stable Minecraft Bedrock Creator documentation and relevant tooling.
9. Use OpenSpec for change planning and specifications; do not introduce a competing spec framework.
10. Prefer Mojang's existing Minecraft Creator Tools over unnecessary custom implementations.

## Repository setup responsibilities
Design and initialize the Git repository, `.gitignore`, Node.js tooling, Bedrock pack scaffolding, project structure, OpenSpec integration, AI coding agent guidance, relevant skills, local preview, automated validation, versioning, packaging, GitHub Actions and documentation.

Choose a maintainable structure, explain important trade-offs and avoid unnecessary architectural complexity.

## Pack identity
- Repo: `asa-minecraft-package`
- Public display name: `Sinbad Selection`
- Content namespace: `sinbad`
- Behavior Pack display name: `Sinbad Selection - Behavior`
- Resource Pack display name: `Sinbad Selection - Resources`
- Release artifact: `asa-minecraft-package-vX.Y.Z.mcaddon`

Generate unique UUIDs for pack headers/modules, store them in version control, and preserve them across releases. Keep established content identifiers stable. Use synchronized manifest versions and appropriate pack dependencies.

## Feature development lifecycle
1. Creative intake: Preserve the original image/drawing and document intended features. Separate explicit user requirements from AI interpretations.
2. Exploration: Use OpenSpec exploration to study the concept, repository capabilities, Bedrock constraints and implementation options. Distinguish JSON-native behavior, Script API logic and browser-only previews.
3. Proposal: Generate an OpenSpec change proposal, design, acceptance criteria and implementation tasks. Cover appearance, behavior, abilities, spawning/acquisition, balance and compatibility where applicable. Require human approval.
4. Implementation: Build against approved requirements, Bedrock Creator documentation and supported tooling. Organize authored files by feature while outputting correct Bedrock pack structures.
5. Verification: Validate manifests, identifiers, models, textures, animations and scripts. Test portable logic independently. Preview in-browser, but never confuse simulations with actual Bedrock runtime testing.
6. Review and release: Review against the approved proposal, run regression tests, package the single complete `.mcaddon`, publish approved releases and archive the OpenSpec change.

## Browser preview strategy
Investigate Mojang Minecraft Creator Tools' viewer/editor first. Provide fast local visualization of assets and animations. Introduce a custom Three.js playground only if justified by requirements official tooling cannot meet. Avoid creating a custom Bedrock game engine.

## Automated verification
Check malformed JSON/manifests, duplicate or invalid identifiers, missing assets/references, broken pack dependencies, TypeScript/test failures, accidental UUID changes, inconsistent versions and packaging failures. Distinguish structural validation from runtime verification.

## Release strategy
Use semantic versioning for project releases, generate one bundled Add-On, support local development builds without public GitHub releases and automate approved GitHub Releases. Preserve the full content catalog. Document safe iOS installation/updating and existing-world backup steps.

## AI skills
Evaluate Mojang Minecraft Creator Tools (including MCP and relevant Bedrock-focused skills) first. Add only skills that demonstrably improve the workflow. Keep OpenSpec the sole specification framework.

## First milestone
1. Valid, installable Sinbad Selection Add-On.
2. Working Behavior Pack and Resource Pack.
3. One simple custom mob as a proof of concept.
4. Working local validation and packaging.
5. Working browser model/asset preview.
6. Working OpenSpec change lifecycle.
7. GitHub Actions producing a downloadable `.mcaddon`.
8. Successful actual Minecraft Bedrock test on a supported device.

## Operating principles
Preserve the child's creative intent, original source images and approved designs. Prefer verifiable behavior and backward compatibility. Avoid overengineering and speculative scope.

## Immediate task
Start by exploring current Mojang Bedrock documentation, Creator Tools and the likely repository architecture. Initialize or plan OpenSpec as appropriate, and produce a proposal for the initial project setup. Present key design decisions, technical constraints and phased milestones before implementing the full solution. Do not generate a large application or custom preview engine until existing tools have been evaluated.
